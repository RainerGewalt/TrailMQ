# TrailMQ 3.2 — release notes (draft)

> **Status: unreleased draft.** 3.2 has not been published. Nothing here
> describes images you can pull today. The published release notes are the
> GitHub release for the tag. This file is the working text they will be
> written from, and the "Open before publication" list at the end is removed
> when they are.

This draft covers what 3.2 changes for someone operating the
`secure-mqtt-core` recipe. Read it before you switch images.

## Changes that need action

### Undeclared MQTT client IDs are refused by default

3.2 refuses a client ID that no binding covers. The setting is
`mqtt_client_id_undeclared`, overridden by `MQTT_CLIENT_ID_UNDECLARED`, and
the default is `refuse`.

- A connection is admitted with a client ID bound to its account, or with an
  empty client ID, for which the server assigns one.
- A refused device sees an answer that looks like a wrong password (MQTT 3.1.1
  return code 5, MQTT 5 `0x87`). The refusal is recorded with the reason
  `client_id_undeclared`.
- Bindings are new in 3.2. Administrators manage them on the **Clients** page
  of the Web UI, which creates exact bindings, or through
  `/api/v1/clients/bindings`, which also creates prefix bindings.
- Configuration-file users without an account and anonymous clients cannot be
  bound. Under `refuse` they must connect with an empty client ID.
- `first_holder` remains as a compatibility mode and applies only when it is
  set explicitly. Another user can take an undeclared ID first and lock a
  device out until an administrator binds the ID.
- An empty `mqtt_client_id_undeclared` in `config.yaml` stops the backend at
  startup. Every start logs the effective mode and where it came from.
- 3.1.2 does not know the key and refuses to start when `config.yaml` sets it.
  The recipe therefore ships it commented out.

Before switching images, run the read-only upgrade preflight from the 3.2
backend image:

```bash
cd recipes/secure-mqtt-core
TRAILMQ_BACKEND_IMAGE=rainergewalt/trailmq-backend:<version> \
  docker compose run --rm --no-deps -T backend \
    preflight client-ids --config /app/config.yaml
```

Exit `0` means no observed client ID would be refused, `1` means at least one
would, and `2` means the check is incomplete or failed. Read the report as a
list of candidates, not as a list of bindings to create:

- The preflight reads audit records within their retention, so a clean result
  means that nothing was observed, not that nothing will be refused. A
  deployment with fixed-ID field devices upgrades through `first_holder`
  whatever the preflight reports.
- An ID that one user held while another was refused it is reported as
  **contested**. The report lists each user with its role (`holder`,
  `contender` or `observed`), counts the ID as impact and recommends no
  binding. Verify which account owns the device before binding: a binding
  disconnects every other user's session that holds the ID.
- A database written by 3.1.2 can over-report. Before 3.2, a refused CONNECT
  also left a connection record, without a user. The preflight cannot tell
  those from admitted ones, so it counts them under "no principal recorded"
  with a note. From 3.2 on, a refused CONNECT leaves no connection record, and
  failed sign-ins are not counted.

The full procedure, including binding and rollback, is in the recipe README
under
[Upgrading to 3.2: client IDs](../../recipes/secure-mqtt-core/README.md#upgrading-to-32-client-ids).

### The Web UI uses server-assigned client IDs

The 3.2 Web UI connects with a client ID the server assigns, so it works
under `refuse`. A 3.1.2 Web UI sets its own `mqttjs_` client ID, so a 3.2
backend under `refuse` refuses its MQTT connection. Backend and
frontend ship as one release: switch both images together.

## Changes to security assumptions

- **`enabled: false` is enforced for configuration-file users.** A user
  written with `enabled: false` in `config.yaml` is now refused on every path,
  including the password fallback, JWT and client certificates.
- **An omitted `enabled` key means enabled.** A configuration user without the
  key is seeded as an enabled account. An account seeded disabled before 3.2
  because the key was omitted stays disabled until an administrator enables it
  or `enabled: true` is written.
- **A configuration reload ends the live sessions of changed configuration
  users.** No product path reloads users at runtime today, so in practice user
  changes still take effect at the next restart.
- **`/api/v1/metrics/prometheus` carries more.** It still answers without
  sign-in, because it is meant for a scraper, and from 3.2 it also carries
  counts from the MQTT decision trace. The recipe's nginx forwards it on the
  published HTTP port. Do not expose that port to untrusted networks.

## Queue accounting

A QoS 1 publish on a queue-enabled topic is acknowledged before its queue row
is written. 3.2 counts every acknowledged queued publish that is not written
to its topic's queue in `rejectedPublishes` on `/api/v1/queue/status`, and
logs it. 3.1.2 left three of those cases uncounted. See
[scenario 6](../scenarios/06-queue-and-dead-letters.md#what-an-acknowledgement-does-not-tell-you).
